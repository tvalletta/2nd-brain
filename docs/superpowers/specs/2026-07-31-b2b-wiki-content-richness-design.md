# Design: Wiki Content Richness (Sub-project B2b)

**Status:** Approved for plan write-up (design conversation complete 2026-07-31, run in minimal-interaction mode per operator instruction; both items in §17 decided 2026-07-31 — see resolutions below)
**Sub-project:** B2b of Sub-project B (Content Richness). B2a (review-note explanatory content, merged) and B2c (person name resolution, unscoped) are separate, not covered here.
**Soft dependency:** Reuses infrastructure introduced by B2a — `createLLMFromConfig(config, stateDir, tier)` (tier-aware LLM factory) and the pre-existing `BudgetTracker`/`createBudgetTrackerFromConfig`. No new runtime dependency; this spec assumes both already exist (they do, merged to `main`).

## 0. Context

B2b had no prior brief beyond a one-line label. This spec starts from scratch: read the specification, then read the real vault (`~/.karpathy/config.json` → `defaults.vaultPath` = `/Users/valletta/Library/CloudStorage/OneDrive-Adobe/Apps/Obsidian Notes`, layout = the `Curated/wiki` production layout) to find the actual B2a-shaped problem — structurally well-formed content that is thin, generic, or frozen at initial-extraction quality. It's there, and in several places the root cause is visible directly in the source code, not just inferred from vault samples.

### 0.1 Concrete evidence — vault content

**Decision notes: 9 of 9 non-index decisions have a completely empty `Outcome` region.** Not even the fallback text the extraction prompt asks for. Example, `Curated/wiki/decisions/executive-summary-preference.md`:

```
## Outcome
%% begin:outcome %%
%% end:outcome %%
```

`src/enrichment/prompts.ts` (the LLM prompt used by `compileEntityPage`) explicitly instructs: *"OUTCOME: (What actually happened as a result, if known. Write "(pending)" if the outcome isn't yet known.)"* — so even the degenerate case should read `(pending)`, not nothing. Every sampled decision (`first-match-wins-provider-selection-for-entire-session.md`, `executive-summary-preference.md`, and 7 others) is empty, never `(pending)`, never resolved. Nothing in the system ever revisits a decision after its initial creation to check whether an outcome has since become known.

**Project hub overviews: 15 of 16 project `_index.md` files literally contain `Pending enrichment.`** — the exact template string from `getOrCreateProjectHub()` (`src/compilation/project-hub.ts`), e.g. `Curated/wiki/projects/carpathi-second-memory/_index.md`:

```
## Overview
%% begin:overview %%
Pending enrichment.
%% end:overview %%
```

This is the same *shape* of problem B2a fixed for review notes — machine-managed prose that was never anything but a placeholder — just in a different subsystem. One project (`2nd-brain`) has a genuinely rich hub, but even there the richness lives in its `project_spec` sub-pages (`product.md`, `technical.md`), not the hub `_index.md` itself, whose `Overview` region still says `Pending enrichment.`.

**Concept glossary: ~45 concepts, effectively none of them synthesized.** `Curated/wiki/concepts/glossary.md` (161 lines) has one section per concept, and the overwhelming majority have exactly one mention, frozen on the single date they were first extracted (`2026-07-24`), verbatim from the source with zero cross-referencing:

```
## LLM Gateway
*Last mentioned: 2026-07-24*
- "An intermediary service that can be used with Claude Code via the ANTHROPIC_AUTH_TOKEN environment variable." — [[2026-04-15-dc77726a]] (2026-07-24)

## LLM Gateway with Fallback
*Last mentioned: 2026-07-24*
- "An automated approach using a LiteLLM proxy that routes requests to an enterprise account first and falls back to Bedrock when needed..." — [[2026-04-15-dc77726a]] (2026-07-24)
```

`LLM Gateway`, `LLM Gateway with Fallback`, `Multi-Provider Fallback`, and `Native Spillover Support` are four separate headings describing overlapping ideas from the same source, never cross-linked. `RCAs` has the *identical* gloss text appended twice from two similarly-named source files, because `upsertConceptMention`'s dedup key is `(concept, sourceRefSlug)`, not content — two distinct-looking source refs with the same underlying sentence both pass.

**`related-concepts` ("Connected Concepts"): empty in 23 of 23 sampled topic notes — 100%.** Including topics whose `current-understanding` region is thousands of characters of well-cited prose that *explicitly names* other topics and entities (`Curated/wiki/topics/provider-selection.md`'s `current-understanding` references `[[Claude Code]]`, the priority hierarchy, and `Claude Max/Enterprise` by name — none of that makes it into `related-concepts`, which renders as nothing between its tags). The raw material for this field is being generated by the LLM every refresh cycle and thrown away.

**Weekly digests: 9 of 11 non-trivial digests are literally empty** (`total_chunks: 0`, body reads `0 chunks, 0 clusters`). Two digests in the same folder (`2026-W21`, `2026-W26`) have 2,482 and 18,677 chunks respectively, so the vault clearly has data in those windows — this looks like a clustering/windowing bug (chunks not landing in the digest's query window), not an LLM-authoring quality problem. Flagged in §16 as out of scope for this spec.

### 0.2 Concrete evidence — code (the actual root causes)

Three of these vault-level gaps trace to verifiable, specific defects, not just "the LLM wrote something thin":

**Bug 1 — `check-confidence-decay.ts` hardcodes the default layout, silently no-ops under `Curated/wiki`.**

```typescript
// src/jobs/handlers/check-confidence-decay.ts
const allFiles = await vault.listMarkdownFiles(`${context.config.layout.wiki}/projects`); // correct
...
for (const slug of projectDirs) {
  const hubDir = `wiki/projects/${slug}`;   // <-- hardcoded, ignores context.config.layout.wiki
  let specFiles: string[];
  try {
    specFiles = await vault.listMarkdownFiles(hubDir);
  } catch {
    continue;   // <-- silently skips every project under Curated/wiki
  }
```

Under the production layout (`layout.wiki = 'Curated/wiki'`), `hubDir` resolves to a path that doesn't exist, `listMarkdownFiles` throws, the `catch` swallows it, and `staleProjects` stays empty forever. This handler is registered and scheduled (`src/jobs/runner.ts`, 60s poll; `src/jobs/types.ts` priority 85) — it *runs* on every tick, it just never finds anything, on this vault or any other vault using a non-default `layout.wiki`.

**Bug 2 — `agent-synthesize-project.ts` has the identical hardcoded-path bug**, one level deeper:

```typescript
// src/jobs/handlers/agent-synthesize-project.ts
const indexPath = `wiki/projects/${projectSlug}/_index.md`;  // <-- hardcoded
...
try {
  currentHub = await vault.read(indexPath);
} catch {
  log.warn('Project hub not found, skipping re-synthesis', { projectSlug });
  return;   // <-- silent no-op under Curated/wiki
}
```

This is the handler that runs the full Opus agent loop to rewrite a project's specs *and* its hub. Even if something else correctly enqueues it (e.g. the incremental-ingest-threshold trigger, which *does* pass a real `projectSlug`), the very first line fails under the production layout and the whole re-synthesis silently no-ops.

**These two bugs, together, are the direct explanation for the 15/16 "Pending enrichment." finding above.** `2nd-brain/product.md`'s own body contains a self-documented audit trail confirming the vault was migrated from the default `wiki/` layout to `Curated/wiki/` at some point (*"All entity pages written to wrong vault path (`wiki/` instead of `Curated/wiki/`)... 4 bugs fixed in `compiler.ts`, `backlinks.ts`, `update-backlinks.ts`, `rebuild-index.ts`, and `indexes.ts`"*) — that fix pass evidently missed these two files. `product.md`'s own `reinforcement_count: 1` frontmatter field is the fingerprint: synthesized exactly once, at creation, and never since, consistent with `check-confidence-decay` never being able to find it stale again. This is CLAUDE.md's own stated rule (*"Layout-aware paths rule — Always use `layoutFromConfig(config)`/`kindToFolder()`; hardcoded `'wiki/'` breaks Curated/wiki/ production layout"*) violated in exactly the two places that would explain the single largest content-richness gap found in this investigation.

**Bug 3 (latent, not yet triggered, but reproducible by inspection) — `topic-refresh.ts` hardcodes a single region name that doesn't match three of the five note types it's wired to refresh.**

```typescript
// src/intelligence/topic-refresh.ts
export const CURRENT_UNDERSTANDING_REGION = 'current-understanding';
...
const currentUnderstanding = extractRegion(body, CURRENT_UNDERSTANDING_REGION) ?? '(no current understanding yet)';
...
nextBody = upsertRegion(nextBody, CURRENT_UNDERSTANDING_REGION, synthesis.current_understanding.trim());
```

`decay-scan.ts`'s `REFRESHABLE_TYPES = new Set(['concept', 'topic', 'project', 'project_spec', 'decision'])` enqueues `topic-refresh` for all five types once a note's retrievability drops below `intelligence.decay.retrievabilityRefresh` (default `0.5`). But `decision` notes have protected regions `context, outcome, people, sources, backlinks` — no `current-understanding`. `project` hubs have `overview, specs, people, sessions, sources, backlinks`. `project_spec` pages have `content, backlinks`. None of them have the region `refreshTopic` reads and writes.

`updateProtectedRegion()` (`src/vault/protected-regions.ts`) appends a brand-new region block to the end of the note when the target region doesn't exist yet:

```typescript
if (openIndex === -1) {
  // Region doesn't exist — append it (always in new format)
  return `${content.trimEnd()}\n\n${openTag}\n${newContent}\n${closeTag}\n`;
}
```

So the first time `topic-refresh` actually fires on a decision or project note (it hasn't yet in this vault — sampled decisions still have retrievability ≈0.81, above the 0.5 threshold — but it inevitably will as they age), it will **bolt a disconnected `current-understanding` section onto the end of a decision or project page** instead of fixing the actually-thin `outcome`/`overview` region. This is the single existing mechanism in the whole system that does real evidence-grounded LLM refresh, and it is currently wired to corrupt three of the five note types it's supposed to help.

### 0.3 What's *not* broken (important context for scoping)

`current-understanding` on `topic`/`concept` notes is genuinely good — 2,000 to 9,400 characters of cited, evidence-grounded prose (`provider-selection.md`, `prioritization.md`, `architectural-best-practices.md`, etc.), because `topic-refresh` is correctly wired for those two types and runs regularly via the decay-scan → topic-refresh cascade. Person entity pages (`Curated/wiki/entities/*.md`) are also reasonably rich — multi-paragraph summaries, timelines, cross-links — produced by `compileEntityPage`'s `person` prompt. This confirms the *mechanism* (retrieval + evidence-grounded LLM synthesis, written into a protected region) works well when it's wired to the right region and actually runs. B2b's job is to extend that working mechanism to the note types and fields it currently misses or corrupts, and to backfill the ~24 notes already stuck at placeholder quality — not to invent a new content-generation approach.

## 1. Goals / Non-Goals

**Goals:**

- **G0 — Fix the two layout-hardcoding bugs** (`check-confidence-decay.ts`, `agent-synthesize-project.ts`) so the pre-existing agent-driven project re-synthesis pipeline actually runs under any configured `layout.wiki`, not just the default. This alone should let `project_spec` pages resume periodic re-synthesis.
- **G1 — Generalize `refreshTopic` into a region-aware refresh** so `decision` notes get their `outcome` (and, when evidence sharpens it, `context`) rewritten, and `project` hub notes get their `overview` rewritten, using the same retrieval + evidence-grounded synthesis `topic`/`concept` notes already get — instead of a mismatched region being appended.
- **G2 — Add a deterministic "thin content" detector** (no LLM) that finds notes whose primary richness region is empty or a known placeholder, and force-enqueues a refresh immediately, independent of retrievability decay — so the ~24 already-thin notes in the vault today get fixed on the next scan cycle rather than waiting months for natural staleness.
- **G3 — Give decision and project refresh their own synthesis prompts**, distinct from the topic/concept "current understanding" framing, each carrying an explicit anti-fabrication instruction (write the honest placeholder if the evidence doesn't support a real answer — never invent an outcome or a status).
- **G4 — Populate `related-concepts` on topic/concept notes** as a byproduct of the same refresh pass, by rendering the neighbor list `topic-refresh` already resolves internally (for its `pending_evidence` cascade) into the region, instead of computing it and throwing it away.
- **G5 — Make concept-glossary mention de-duplication content-aware**, not just source-ref-aware, so re-ingesting near-duplicate source material doesn't produce literal duplicate mention lines.
- **G6 — Synthesize a short "why this matters" rollup for concepts that accumulate enough mentions** to warrant it, replacing the raw first-mention gloss as the primary description once there's enough evidence, while leaving one-off concepts exactly as they are today (no LLM cost for single mentions).

**Non-goals:**

- **Concept merging/canonicalization** across near-duplicate headings (`LLM Gateway` / `LLM Gateway with Fallback` / `Multi-Provider Fallback`) — this is an entity-dedup-shaped feature with its own review/approval workflow, structurally similar to Sub-project A's entity-merge work. Flagged as likely future work in §16, not designed here.
- **Fixing empty weekly digests** (9/11 show `0 chunks, 0 clusters`) — root-caused in §0.1 as a data-availability/windowing bug in the clustering pipeline, not a content-richness/LLM-authoring problem. Separate bug, not this spec's mechanism.
- **The duplicate-backlink-block rendering bug** observed in `Bryan Pino.md` (`### From Wiki` appearing twice in sequence with repeated lines) — a deterministic-maintenance bug in the backlinks scanner, unrelated to LLM-authored richness. Flagged, not fixed here.
- **B2c (person name resolution)** — separate spec, someone else's scope.
- **A `project_spec`-targeting cheap fallback refresh** — `project_spec` content stays owned exclusively by the (now-fixed) `agent-synthesize-project` pipeline; it is explicitly *excluded* from the new generic refresh-target registry (see §5, "Why `project_spec` is excluded"). Whether a cheaper stop-gap is needed for very-low-activity projects is called out as a genuine open question in §17.
- **Auto-approving or bypassing existing review/protected-region rules.** Refreshed regions remain machine-managed content per spec §12.2 (automation may update deterministic/machine-managed sections); nothing here changes the human-review gates in FR-6 (contradiction resolution, duplicate merges, alias collapses, destructive edits — none of which this spec touches).

## 4. Component 1 — `REFRESH_TARGETS` registry

**File:** `src/intelligence/refresh-targets.ts` (new)

Centralizes, per note `type`, everything `refreshTopic` and `decay-scan`/`rot-scan` need to act correctly instead of assuming one region name fits every type. Modeled on `entity-compiler.ts`'s existing `KIND_SECTIONS` map (which already encodes "decision → context/outcome/people/sources" — this spec reuses that same taxonomy, scoped down to the one *primary* region each type's refresh pass should own) and on B2a's `PROMPTS`-keyed-by-kind pattern.

```typescript
import { z } from 'zod';

export interface RefreshEvidence {
  title: string;
  existingPrimary: string;   // current content of the primary region (may be a placeholder)
  existingSecondary?: string; // e.g. decision's `context`, used as read-only grounding
  evidenceBlock: string;      // pre-formatted, numbered retrieval hits (same shape topic-refresh already builds)
}

export interface RefreshSynthesis {
  primary: string;             // rewritten content for the primary region
  secondary?: string;          // optional rewrite of the secondary region (decision's context only)
  contradictions: Array<{ ref: string; reason: string }>;
  newSources: string[];
}

export interface RefreshTarget {
  /** The one protected region this refresh pass rewrites. */
  primaryRegion: string;
  /** Optional second region this type's prompt is also allowed to touch (decision only: `context`). */
  secondaryRegion?: string;
  /** Human label used in prompts/logs. */
  label: string;
  /** Exact strings (case-insensitive, trimmed) that count as "not yet written" for this type. */
  placeholderStrings: string[];
  /** Below this many non-whitespace characters (after stripping wikilink brackets), also counts as thin. */
  minCharFloor: number;
  buildPrompt(evidence: RefreshEvidence): string;
  responseSchema: z.ZodType<{
    primary: string;
    secondary?: string;
    contradictions: Array<{ ref: string; reason: string }>;
    new_sources: string[];
  }>;
}

export function isPlaceholderContent(target: RefreshTarget, rawContent: string | null): boolean {
  const trimmed = (rawContent ?? '').trim();
  if (trimmed.length === 0) return true;
  if (target.placeholderStrings.some((p) => p.toLowerCase() === trimmed.toLowerCase())) return true;
  const stripped = trimmed.replace(/\[\[|\]\]/g, '');
  return stripped.length < target.minCharFloor;
}

const ConceptTopicSchema = z.object({
  primary: z.string(),
  contradictions: z.array(z.object({ ref: z.string(), reason: z.string() })).default([]),
  new_sources: z.array(z.string()).default([]),
});

const DecisionSchema = z.object({
  primary: z.string(),        // outcome
  secondary: z.string().optional(), // context, only if meaningfully sharpened
  contradictions: z.array(z.object({ ref: z.string(), reason: z.string() })).default([]),
  new_sources: z.array(z.string()).default([]),
});

const ProjectSchema = z.object({
  primary: z.string(),        // overview
  contradictions: z.array(z.object({ ref: z.string(), reason: z.string() })).default([]),
  new_sources: z.array(z.string()).default([]),
});

export const REFRESH_TARGETS: Record<'concept' | 'topic' | 'decision' | 'project', RefreshTarget> = {
  concept: {
    primaryRegion: 'current-understanding',
    label: 'Current Understanding',
    placeholderStrings: ['(no current understanding yet)', ''],
    minCharFloor: 40,
    buildPrompt: buildConceptTopicPrompt,
    responseSchema: ConceptTopicSchema,
  },
  topic: {
    primaryRegion: 'current-understanding',
    label: 'Current Understanding',
    placeholderStrings: ['(no current understanding yet)', ''],
    minCharFloor: 40,
    buildPrompt: buildConceptTopicPrompt,
    responseSchema: ConceptTopicSchema,
  },
  decision: {
    primaryRegion: 'outcome',
    secondaryRegion: 'context',
    label: 'Outcome',
    placeholderStrings: ['', '(pending)'],
    minCharFloor: 10,
    buildPrompt: buildDecisionPrompt,
    responseSchema: DecisionSchema,
  },
  project: {
    primaryRegion: 'overview',
    label: 'Overview',
    placeholderStrings: ['', 'pending enrichment.'],
    minCharFloor: 20,
    buildPrompt: buildProjectPrompt,
    responseSchema: ProjectSchema,
  },
};
```

`project_spec` is intentionally absent from this map — see the callout in §5.

**Why the placeholder/floor combination, not just an exact string match:** an exact-string list alone is fragile — a future rewording of "Pending enrichment." anywhere upstream would silently escape detection forever. A pure character-count floor alone would misfire on legitimately short-but-complete content (e.g., a one-sentence decision outcome that's genuinely all there is to say). Combining both — exact match on the two placeholder families that are known to exist today, *and* a low character floor as a backstop — covers both the known cases and future near-misses without the doc needing to guess every future wording.

## 5. Component 2 — Generalizing `refreshTopic`

**File:** `src/intelligence/topic-refresh.ts` (modified)

The exported function name, its signature (`refreshTopic(deps, notePath, options)`), the job type string `topic-refresh`, and `src/jobs/handlers/topic-refresh.ts` (the handler) are **all unchanged** — this is a purely internal generalization, matching B2a's pattern of additive, backward-compatible changes to shared infrastructure.

```typescript
import { REFRESH_TARGETS, isPlaceholderContent, type RefreshTarget } from './refresh-targets.js';

export async function refreshTopic(
  deps: RefreshDeps,
  notePath: string,
  options: RefreshOptions = {},
): Promise<RefreshResult> {
  ...
  const raw = await deps.vault.read(notePath);
  const { data, body } = parseNote(raw);
  const fm = data as Record<string, unknown>;
  const noteType = typeof fm.type === 'string' ? fm.type : 'topic';

  const target: RefreshTarget | undefined = (REFRESH_TARGETS as Record<string, RefreshTarget>)[noteType];
  if (!target) {
    // Unknown/unsupported type (e.g. project_spec) — bump last_verified and
    // clear pending_evidence so the queue doesn't spin forever, but do not
    // touch the body. Mirrors the existing "no evidence found" no-op branch.
    fm.last_verified = nowIso;
    fm.pending_evidence = [];
    fm.pending_evidence_count = 0;
    await deps.vault.atomicWrite(notePath, serializeNote(fm, body));
    return { notePath, retrievedCount: 0, contradictionCount: 0, newSourcesAdded: 0,
      stabilityBefore: undefined, stabilityAfter: 0, lastVerified: nowIso,
      pendingCleared: 0, neighborsCascaded: 0 };
  }

  const existingPrimary = extractRegion(body, target.primaryRegion) ?? '';
  const existingSecondary = target.secondaryRegion ? (extractRegion(body, target.secondaryRegion) ?? '') : undefined;
  ...
  const queryText = [title, tldr, existingPrimary, existingSecondary].filter(Boolean).join('\n');
  const hits = await retrieve({ store: deps.store, config: deps.config }, queryText, { topK, filter: (h) => h.doc_id !== notePath });
  ...
  const evidenceBlock = hits.map((h, i) => `[${i + 1}] (${h.doc_id}, updated ${h.updated_at})\n${h.text.slice(0, 1200)}`).join('\n\n');
  const prompt = target.buildPrompt({ title, existingPrimary, existingSecondary, evidenceBlock });

  let synthesis;
  try {
    synthesis = await deps.llm.extractStructured(prompt, target.responseSchema);
  } catch (err) {
    if (err instanceof TransientLLMError) throw err;
    throw new Error(`refresh failed for ${notePath}: ${(err as Error).message}`);
  }

  let nextBody = body;
  nextBody = upsertRegion(nextBody, target.primaryRegion, synthesis.primary.trim());
  if (target.secondaryRegion && synthesis.secondary) {
    nextBody = upsertRegion(nextBody, target.secondaryRegion, synthesis.secondary.trim());
  }
  ... // sources region, stability, contradictions: unchanged from today's logic, now generic over `target`

  // G4: for concept/topic only, render resolved cascade-neighbors into related-concepts.
  if ((noteType === 'concept' || noteType === 'topic') && hasProtectedRegion(nextBody, 'related-concepts')) {
    const neighborLines = await resolveNeighborLines(deps.vault, synthesis.primary, notePath);
    nextBody = upsertRegion(
      nextBody,
      'related-concepts',
      neighborLines.length > 0
        ? neighborLines.join('\n')
        : '_No connected concepts identified in the current synthesis._',
    );
  }
  ...
}
```

`resolveNeighborLines()` factors out logic that already exists inline in the cascade-depth-1 block (lines ~226–260 of the current file): extract outlinks from the newly-written prose via `extractOutlinks()`, resolve each via `buildEntityIndex()`/slug/alias lookup, skip self-references and duplicates. Today that logic's only output is a side effect (`markDirty` on each neighbor). This change makes it return the resolved `{ path, name }` list so the SAME computation can *also* render a `- [[path]]` bullet list into `related-concepts`, instead of computing neighbor identities and discarding them after the markDirty call. No new extraction or retrieval work — this is populating an existing structural field from data the refresh pass was already computing and throwing away (§0.1's specific finding).

**Prompt bodies** (in `refresh-targets.ts`, called out here for the anti-fabrication framing that's the actual design point):

```typescript
function buildConceptTopicPrompt(e: RefreshEvidence): string {
  return `You are refreshing a topic note in a personal knowledge base.

Topic: ${e.title}
Current understanding (from existing note):
"""
${e.existingPrimary || '(no current understanding yet)'}
"""
```

**The anti-fabrication instruction is the load-bearing design decision here, not an afterthought.** A knowledge base whose entire value proposition rests on provenance (spec §5.2: *"Every nontrivial claim in `wiki/` MUST carry provenance"*) is actively harmed by a refresh mechanism that would rather invent a plausible-sounding decision outcome or project status than admit the evidence doesn't support one. The existing `(pending)` convention in `enrichment/prompts.ts` already establishes this precedent for decisions; this spec extends the same discipline to projects (`"Pending enrichment."` is deliberately kept as the acceptable honest answer, not something to be stamped out at all costs) and makes it explicit in every refresh prompt rather than leaving it implicit.

**Why `project_spec` is excluded from `REFRESH_TARGETS`:** its content region (`content`) is intentionally owned by `agent-synthesize-project` — a full multi-turn Opus agent loop with tool use across the entire conversation-digest corpus for that project, materially more expensive and more capable than a single retrieval+CoD rewrite. Once Component 0's path fix lands, that pipeline resumes running on its own schedule (`check-confidence-decay`, 60s poll) and via the incremental-ingest threshold. Routing `project_spec` through the cheaper generic refresh as well would risk a lower-quality rewrite clobbering richer agent-authored content, or at minimum wasted budget on a type that already has its own, better-suited refresh loop. `decay-scan.ts` (§6) stops blindly trusting `REFRESHABLE_TYPES` for the enqueue decision and instead checks `REFRESH_TARGETS[type]` — `project_spec` naturally falls through to "retrievability/archive scoring only, no generic-refresh enqueue," which is exactly the intended behavior.

### 9.1 Content-aware dedup (G5)

```typescript

  name: string;
  mentions: ConceptMention[];
  synthesis?: string;            // NEW — rollup line, present once mention count has crossed the threshold

  mentionCount: number;

  options: { synthesisThreshold?: number } = {},

  ...

  const existing = entries.get(key);

  if (sameSourceRef || sameGlossText) {

  }
  ...
  const threshold = options.synthesisThreshold ?? 3;

```

`sameGlossText` is a deliberately blunt check — case-insensitive exact match on the normalized gloss, scoped to mentions of the *same concept heading* only (never cross-concept). It will not catch near-duplicate paraphrases (that's a harder problem, arguably part of the deferred concept-merging work in §16), but it directly fixes the observed `RCAs` case (identical sentence, two source refs) at zero cost — no LLM call, no new state.

### 9.2 Rendering the synthesis line

```typescript
function renderGlossary(entries: Map<string, ConceptEntry>): string {
  return [...entries.values()].sort((a, b) => a.name.localeCompare(b.name))
    .map((entry) => {
      const lastMention = entry.mentions[entry.mentions.length - 1];
      const synthesisLine = entry.synthesis ? `*${entry.synthesis}*\n` : '';
      const mentionLines = entry.mentions.map((m) => `- "${m.gloss}" — [[${m.sourceRef}]] (${m.date})`).join('\n');
      return `## ${entry.name}\n*Last mentioned: ${lastMention?.date ?? 'unknown'}*\n${synthesisLine}${mentionLines}`;
    })
    .join('\n\n');
}
```

`parseGlossary()` gains a matching optional line-parse: a line matching `/^\*(?!Last mentioned:)(.+)\*$/` immediately after the "Last mentioned" line, present before the first mention bullet, is read back into `entry.synthesis`. `synthesizedAtCount` is persisted as a small suffix on the synthesis line itself (`*<synthesis text> (as of 5 mentions)*`) rather than as separate frontmatter, since the glossary file has no per-concept frontmatter to hang it on — the whole file is one `index`-typed note. A regex capturing the trailing `(as of N mentions)` parenthetical extracts `synthesizedAtCount` back out on parse; its absence just means "never synthesized," consistent with `entry.synthesis` being `undefined`.

### 9.3 The `glossary-synthesize` job

**File:** `src/jobs/handlers/glossary-synthesize.ts` (new)

```typescript
import type { JobHandler } from '../types.js';
import { createLLMFromConfig } from '../../enrichment/llm-factory.js';
import { createBudgetTrackerFromConfig } from '../../shared/budget.js';
import { resolveStateDir } from '../../config/defaults.js';

import { TransientLLMError } from '../../shared/errors.js';
import { createLogger } from '../../shared/logger.js';

const log = createLogger('glossary-synthesize');

export const glossarySynthesizeHandler: JobHandler = {
  async execute(job, ctx) {
    const conceptName = job.payload.conceptName as string | undefined;
    if (!conceptName) { log.warn('glossary-synthesize: missing conceptName'); return; }
    if (!ctx.config.intelligence.richness.enabled) return;

    const budget = createBudgetTrackerFromConfig(ctx.config, ctx.projectRoot);
    if (!budget.tryReserve('fast')) {
      log.info('glossary-synthesize skipped: fast-tier budget exhausted', { conceptName });
      return; // no queue to preserve — next ingest that grows this concept re-fires the gate naturally
    }

    const stateDir = resolveStateDir(ctx.config);
    const llm = createLLMFromConfig(ctx.config, stateDir, 'fast');
    try {
      await synthesizeConceptEntry(ctx.vault, ctx.config.layout, conceptName, llm);
    } catch (err) {
      if (err instanceof TransientLLMError) throw err;
      log.warn('glossary-synthesize failed', { conceptName, error: (err as Error).message });
    }
  },
};
```

## 13. Edge cases and failure modes

- **A decision/project refresh finds zero retrieval hits** (e.g. an orphaned decision nobody else references): falls into the existing "no evidence found" branch in `refreshTopic` — `last_verified` is bumped, `pending_evidence` cleared, body untouched. This means a genuinely evidence-starved decision stays at `(pending)`/`Pending enrichment.` forever, which is correct (per §5's anti-fabrication principle) rather than a bug to fix.
- **A `TransientLLMError` during any new refresh path** (decision, project, or glossary synthesis) propagates exactly like every other LLM call site fixed in the VPN-retry work and B2a — never caught and converted into a placeholder. The `glossary-synthesize` handler explicitly rethrows; `refreshTopic`'s existing try/catch (unchanged) already does this for all types generically.
- **Two concurrent `compile-entities` jobs for the same concept both cross the synthesis threshold in the same tick:** the `dedupeKey: glossary-synthesize:${key}:${mentionCount}` includes the exact mention count at crossing time, so two crossings at *different* counts (e.g. 3 and 6, if a burst of ingests lands between reads) each get their own job — correct, since each represents genuinely new evidence. Two crossings at the *identical* count collapse to one job via the existing job-queue dedup behavior (spec §8.3).
- **A note's `type` frontmatter is missing or unrecognized** (e.g. a hand-authored note dropped into `wiki/decisions/` without a `type` field): `decay-scan`'s existing `REFRESHABLE_TYPES.has(type)` check (unchanged) already skips it before this spec's new `REFRESH_TARGETS[type]` lookup is ever reached — no new failure mode introduced.
- **The `related-concepts` backfill (§6) resolves zero neighbors** for a topic whose `current-understanding` genuinely doesn't wikilink anything (rare, but possible for a narrowly-scoped topic): writes the explicit `_No connected concepts identified in the current synthesis._` sentinel rather than leaving the region empty — this is itself a fix for the "looks broken vs. confirmed empty" ambiguity a truly-empty region creates, distinguishing "never checked" from "checked, nothing found."
- **`isPlaceholderContent`'s `minCharFloor` false-positives on a legitimately terse-but-complete answer** (e.g. a two-word decision outcome like "Approved. Shipped."): would trigger one unnecessary refresh call, which is harmless — the refresh either confirms the short answer is still accurate (no-op rewrite) or genuinely improves it. This is a one-time cost, not a recurring one, since the note's `last_verified` is bumped either way and it won't be flagged as thin again on the next scan (its content no longer matches `isPlaceholderContent`, since the LLM's confirmed rewrite is very unlikely to be under the same character floor `<10`/`<20` chars used here — chosen deliberately low to bias toward false negatives, not false positives).
- **Glossary content-hash dedup (`sameGlossText`) collapsing two *genuinely distinct* mentions that happen to use identical phrasing** (e.g. two unrelated sources both extracting the exact boilerplate sentence "A recurring meeting or event where teams demo their work" for "Sprint Review"): accepted false-negative — the second mention's *source* is lost, but the concept's definition is unchanged either way, and this is a narrower, much rarer failure mode than the current 100%-of-duplicates-kept behavior it replaces.

- `concept-glossary.ts`: `upsertConceptMention` — identical gloss text from a different `sourceRef` is skipped (the RCAs regression case, reproduced verbatim from the real vault sample); `crossedSynthesisThreshold` is `false` below the configured threshold, `true` exactly at it, `false` again immediately after (until mention count grows by another full threshold), `true` again at `2×threshold`. `synthesizeConceptEntry`: given a mocked LLM response, the concept's section gains the synthesis line above its mention list, mention list itself is untouched; `parseGlossary` round-trips a synthesis line (parse → render → parse produces an identical `ConceptEntry`).
- `glossary-synthesize.ts` (job handler): budget-exhausted → early return, no LLM call constructed (mirrors B2a's equivalent test); `TransientLLMError` from the LLM call propagates out of `execute()` unmodified; `intelligence.richness.enabled: false` → early return, no LLM call constructed.
- `compile-entities.ts`: a concept mention that crosses the threshold enqueues `glossary-synthesize` with the expected `dedupeKey`/payload; one that doesn't cross it does not enqueue anything (regression: existing concept-mention tests for this handler must keep passing unmodified).
- `check-confidence-decay.ts` / `agent-synthesize-project.ts`: a regression-style test constructing a `KarpathyConfig` with a *non-default* `layout.wiki` (e.g. `'Curated/wiki'`, matching the real production config) and a project hub/spec under that path — asserting the handler actually finds/reads it (this is the test that would have caught Bug 1/Bug 2 originally; today's existing tests for these two handlers evidently only exercise the default layout, which is exactly how these bugs shipped unnoticed).

## 16. Explicitly deferred

- **Concept merging/canonicalization** across near-duplicate glossary headings (`LLM Gateway` / `LLM Gateway with Fallback` / `Multi-Provider Fallback` / `Native Spillover Support`) — a distinct, entity-dedup-shaped feature (candidate detection, confidence scoring, a review/approval queue) structurally similar to Sub-project A's entity-merge work, not a content-*richness* problem in the sense this spec addresses. Worth scoping separately once B2b's mechanisms are in place and the glossary has had time to accumulate more evidence of exactly which headings collide.
- **Fixing empty weekly digests** (9/11 non-trivial digests showing `0 chunks, 0 clusters`) — root-caused in §0.1 as a clustering/windowing data-availability bug, not an LLM-authoring quality problem; recommend a separate, narrowly-scoped bug investigation into `src/intelligence/digest.ts`'s chunk-window query against the embedding store.
- **The duplicate-backlink-block rendering bug** (`Bryan Pino.md`'s `### From Wiki` heading appearing twice in immediate succession with overlapping content) — a deterministic-maintenance defect in the backlinks scanner (`src/maintenance/backlinks.ts` / `update-backlinks` handler), unrelated to LLM-authored content richness. Flagged for a fast-follow, not designed here.
- **A cheap fallback refresh path for `project_spec` pages that never accumulate enough conversation-digest volume** to trigger `agent-synthesize-project` meaningfully — see the open question in §17.
- **B2c (person name resolution)** — separate spec, out of scope by definition.

## 17. Decisions (resolved 2026-07-31, operating in minimal-interaction mode)

- **Low-activity `project_spec` pages: decided (a), accept as-is.** No fallback refresh added for `project_spec` in this spec. Low-activity projects staying thin is the correct behavior — there's genuinely little to synthesize yet — and the hub's own `overview` region still gets a reasonable one-paragraph status via the new generic `project` target regardless. Revisit only if a real project is observed stuck thin *despite* having enough digest volume to warrant `agent-synthesize-project` (which would point at a different bug, not a scoping gap).
- **Concept-merging timing: decided, defer.** Stays out of this spec's scope per §16, notwithstanding the four visible near-duplicate `LLM Gateway` headings in the sample data. It's a materially different mechanism (candidate detection + human-reviewed merge, entity-dedup-shaped) than the LLM-authored prose-quality work this spec does, and bundling it in would blur one sub-project's review surface into two unrelated concerns. Recommend scoping it as its own follow-on sub-project once B2b's glossary changes have had time to accumulate more evidence of which headings actually collide.
