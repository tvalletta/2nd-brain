# Curation Effectiveness Audit — Final Scorecard

**Scope:** Karpathy Second Memory (`/Users/valletta/dev/2nd-brain`), audited against the real production vault at `/Users/valletta/Library/CloudStorage/OneDrive-Adobe/Apps/Obsidian Notes` (the `Curated/` layout).
**Period covered:** Design conversations 2026-07-23 through 2026-07-31; all eight sub-projects below are complete and merged to `main`.
**Sub-projects:** A (Quality Layer Activation), B1 (Taxonomy & Extraction Redesign), VPN-aware LLM retry, B2a (Review-Note Explanatory Content), B2b (Wiki Content Richness), B2c (Person Name Resolution), C (Draft/Archival Lifecycle), D (Research Queue Redesign).

This document answers the questions the audit set out to answer: how effective and useful is the system, how often and for what purpose is it actually used, is the right content being curated and connected, is the machinery actually running, and what does it cost. Every claim below traces to a specific finding in one of the eight design docs (`docs/superpowers/specs/2026-07-2[3-8]*-design.md`, `docs/superpowers/specs/2026-07-31-*-design.md`) or to a specific commit in this repo's history. Where something can't be verified, that's stated explicitly rather than guessed.

---

## Executive summary

**Is it running?** Mostly not, and the audit found this in layers. The three pieces of quality-control machinery that existed in code before this audit — contradiction/duplicate detection, entity-dedup auto-merge, and the significance gate — were fully built and entirely inert: nothing scheduled the detectors, `config.maintenance.reviewEnabled` was read in exactly one place in the whole codebase and never acted on, and the production ingest path bypassed the significance gate completely. Sub-project A wired all three into place. But the single largest finding of the entire audit is that **93.7% of all ingested source content (11,133 of 11,876 files) never advances past the very first stage of the ingest pipeline** — it sits at `ingest_status: detected` forever, with literal placeholder text (`"Pending extraction."`, `"No entities extracted yet."`) still in the file. This is a scheduler/throughput problem, not a curation-logic problem, and it was deliberately **not fixed** by any of the eight sub-projects — flagged in Sub-project C's design doc as "the single most consequential finding of the whole audit" and left as an urgent, separate follow-up. Beyond that: the research-queue mechanism (`research-propose`/`research-execute`) had run its proposal half reliably for 2.5 months but had **never once executed a single research round in production** because two of its three approval surfaces silently wrote to a nonexistent legacy path and the executor was never scheduled. The `karpathy review approve/reject` commands had been silently no-op'ing on every real review item since the review workflow first shipped. Both are now fixed.

**Is the right stuff being curated?** No, for most of the vault's non-topic content, though this has since been substantially repaired. Of the vault's ~139 curated wiki notes as of the original audit, only the 23 `topic` notes were doing real, evidence-grounded synthesis. The other ~116 (entity/concept/decision/tool/organization pages) were frozen at a single backfill pass from 2026-05-15: concept pages were one-line stubs with verbatim-duplicated boilerplate; 9 of 9 real decision notes had a completely empty `Outcome` region (not even the documented "(pending)" fallback); 15 of 16 project hub pages literally read "Pending enrichment."; 9 of 11 non-trivial weekly digests showed `0 chunks, 0 clusters`. Sub-project B1 and B2b together traced these to specific, fixable code defects (a schema field silently dropped by Zod, a prompt asking for the wrong section labels, two hardcoded `wiki/` paths) and fixed the ones that were fixable without redesigning the extraction pipeline.

**Are things properly connected?** No, in several independent ways, most now fixed. `superseded_by` existed in the schema and appeared 215 times in the vault — always as an empty array; it had never been written to once. `related-concepts` was empty in 23 of 23 sampled topic notes, even when the topic's own prose explicitly named the concepts that belonged there — the LLM was generating the right data every refresh cycle and the code was throwing it away. `project_status`'s `archived`/`completed` index buckets were fully built and rendered in the UI but had zero producers anywhere in the codebase — every project was hardcoded to `active` forever. And the entity-dedup mechanism had a proven, real blind spot: a bare first name ("Bryan") mentioned in one document and a full name ("Bryan Pino") in an unrelated document were invisible to both of the system's duplicate-detection mechanisms, because both require either near-identical text or shared source references — Tom had already hit this once and manually merged around the tooling before the audit found it.

**Cost:** Before this work, LLM cost was near-zero mostly because the mechanisms that would have spent money weren't running. A real tiered budget system is now in place: `BudgetTracker` enforces daily per-tier call caps (defaults: 200 fast / 50 medium / 10 heavy), every new feature reserves from it before calling an LLM, and a cheap-first-with-escalation pattern (try Haiku, escalate to Sonnet only if confidence is low) is now the standard shape for review analysis, research execution, and glossary synthesis. A connectivity-probe cache avoids burning retries against a LiteLLM proxy that's down because of VPN disconnection, and jobs that fail for genuinely transient reasons (network, 429, 5xx) now retry indefinitely with capped backoff instead of being silently discarded after three tries in ~7 seconds.

**How often and for what is it actually used?** Ingestion capture is heavy and continuous — session logs and raw source material have flowed in steadily since 2026-05-14 (11,876 files as of the audit, still growing daily through 2026-07-30). But the curation/synthesis layer riding on top of that capture was, for most content types, either dormant (quality gates), never-invoked (research execution, review approve/reject), or producing placeholder output (decisions, project hubs, most concepts). The one part of the system that was working as designed — topic-note synthesis — is genuinely good: 2,000–9,400 characters of cited, evidence-grounded prose per topic, refreshed on a real retrieval-plus-LLM cycle. That gap between "one subsystem works well" and "most subsystems never ran" is the throughline of this whole audit.

## 2. Was the right stuff being curated?

**Concept pages (before B1/B2b):** ~37 individual concept pages, thin, frozen at first extraction, sometimes verbatim-identical boilerplate across different concepts. B1 consolidated all 37 into a single `Curated/wiki/concepts/glossary.md` (one section per concept, appending mentions instead of spawning pages). By the time B2b audited it a week later, the glossary had grown to ~45 concepts — and **effectively none were synthesized**: the overwhelming majority had exactly one mention, frozen on the date first extracted, verbatim from source, zero cross-referencing. Four separate headings (`LLM Gateway`, `LLM Gateway with Fallback`, `Multi-Provider Fallback`, `Native Spillover Support`) described overlapping ideas from the same source and were never cross-linked. One concept (`RCAs`) had the identical gloss text appended twice because the original dedup key was `(concept, sourceRef)`, not content. B2b added content-aware dedup and a threshold-triggered LLM rollup synthesis (fires once a concept crosses 3 mentions, refires every 3 more).

**Decision notes:** 9 of 9 real decision notes (excluding index pages) had a completely empty `Outcome` region — not even the documented `"(pending)"` fallback the extraction prompt explicitly asks for. Root cause (B2b): the LLM synthesis prompt asked for sections labeled `SUMMARY/PEOPLE/PROJECTS/TOPICS/SOURCES`, but a decision note's actual protected regions are `context/outcome/people/sources` — the label mismatch meant `context`/`outcome` had never once been touched by synthesis since page creation, on any decision note in the vault. B1 separately found only 3 of 9 decision notes were genuine committed choices; the rest were process trivia or a meta-decision titled "Audit the audit." B2b fixed the prompt-label mismatch and generalized the refresh mechanism (originally `topic`/`concept`-only) to also target `decision.outcome` and `decision.context`, with an explicit anti-fabrication instruction: write the honest `(pending)` if the evidence doesn't support a real answer.

**Project hubs:** 15 of 16 project `_index.md` files literally contained the exact template string `"Pending enrichment."` in their `Overview` region. Root cause (B2b): two independent hardcoded-`wiki/`-path bugs in `check-confidence-decay.ts` and `agent-synthesize-project.ts` meant the agent-driven project re-synthesis pipeline — a full multi-turn Opus tool-use loop — silently no-op'd under the real vault's non-default `Curated/wiki` layout, every time, for every project. `2nd-brain/product.md`'s own body contained a self-documented audit trail confirming an earlier, incomplete layout migration ("4 bugs fixed in `compiler.ts`, `backlinks.ts`, `update-backlinks.ts`, `rebuild-index.ts`, and `indexes.ts`") that had missed these exact two files. B2b fixed both hardcoded paths and additionally generalized the refresh mechanism to give project hubs their own `overview`-targeting synthesis pass.

**Weekly digests:** 9 of 11 non-trivial digests show `0 chunks, 0 clusters` — literally empty. Two digests in the same folder (`2026-W21`, `2026-W26`) have 2,482 and 18,677 chunks respectively, proving the vault has real data in those windows; this points to a clustering/windowing bug in `src/intelligence/digest.ts`, not an LLM-authoring problem. **Explicitly deferred** — flagged in B2b as a separate, narrowly-scoped investigation, not fixed here.

**Person entities:** 12 of 21 real person pages (57%) were bare first names ("arevik", "gagik", "hovhannes"...) or literal Slack handles ("brownf", "mewing", "pvaughn") with empty `aliases: []`. B2c fixed the extraction gap (Slack profile links carry stable, free, already-present identity — thrown away before extraction) and extended the name-matching algorithm (honorific stripping, a curated nickname table, initials matching), plus added a person-scoped cross-document name-variant detector that queues low-confidence candidates for human review rather than auto-merging.

**Review notes:** all four kinds (contradiction, duplicate, ambiguous entity, uncertain drop) wrote either fully static text (`"Pending human review."`) or generic templated text with zero LLM judgment of whether the underlying heuristic was even a true positive. B2a unified all four onto one write path and added real LLM-generated analysis (verdict + 2-3 sentences of grounded reasoning + confidence), with a cheap-first-then-escalate pattern (Haiku, escalating to Sonnet on low confidence).

**Research candidates:** ~19 of the 30 real pending candidates were orphaned by Sub-project B1's own concept-glossary consolidation — they pointed at individual concept pages (`{slug}.md` under `wiki/concepts/`) that stopped existing the moment B1 shipped, and the carry-forward logic never checked whether a candidate's backing page still existed. If any had been approved and executed, the executor would have silently recreated an individual concept page inside the now glossary-consolidated folder — a split-brain representation of the same concept, one sub-project's mechanism undoing another's. Sub-project D added both a propose-side purge (drops orphaned candidates each cycle) and a defense-in-depth write-guard in the executor that refuses (throws) rather than silently forking a duplicate page.

## 3. Were things properly connected?

- **`superseded_by`:** 215 occurrences in the real vault, **100% empty arrays**. The field CLAUDE.md documents as a shipped part of the lifecycle had never been written to once. Sub-project C gave it its first real producer (the archive queue's "supersede" resolution), but **it still has no reader anywhere** — no code displays "this note was superseded by X"; `get_note`, `search`, etc. don't special-case it. Writer exists, consumer doesn't.
- **`related-concepts` ("Connected Concepts"):** empty in 23 of 23 sampled topic notes — 100%, including topics whose `current-understanding` region is thousands of characters of cited prose that explicitly names other topics and entities by name. The raw material (resolved neighbor entities) was being computed by `topic-refresh`'s existing cascade logic every refresh cycle, used only for a side effect (`markDirty` on neighbors), and thrown away rather than rendered into the field it belongs in. B2b fixed this — the same computation now also renders a `- [[path]]` bullet list into `related-concepts`.
- **Person-entity duplicate blind spot (proven, not hypothetical):** `Bryan Pino.md` is the vault's one clear evidence trail of a real merge — `calibration.md`'s own frontmatter still references a `bryan.md` page that no longer exists on disk, but `Bryan Pino.md`'s `aliases` array contains only `pino`, not `bryan`. That absence proves the merge was done by hand, not through `mergeEntities()` (which would have added the source's `canonical_name` as an alias). Concretely: a fresh mention of bare "Bryan" today would resolve as `status: 'new'` and silently auto-create a duplicate `bryan.md` — both of the system's duplicate-detection mechanisms (ingest-time `resolveEntity`, periodic `detectMergeCandidates`) share the identical blind spot, because both require either near-identical text or shared source references, and a name-variant mention in a different, unrelated document has neither. B2c closed this with a person-scoped, no-shared-source-required detection tier that always routes to human review (never auto-merges).
- **`project_status`'s "archived"/"completed" index buckets:** fully built rendering path (`indexes.ts`'s `renderProjectsCategory` groups into `Active | Completed | Archived | Other`), confirmed live in the real vault's `Curated/wiki/projects/_index.md` — but written by exactly 3 sites in the whole codebase, and every one of them writes `'active'`. No code path anywhere had ever written `'archived'` or `'completed'`. Sub-project C's archive-queue "archive" decision is the first real producer of the `archived` value (writes `status` and `project_status` together, in lockstep, for projects).
- **`NoteStatus`'s `rejected` enum value:** defined in the schema, zero producers anywhere in the codebase. `review_state` had a real approve/reject transition, but neither touched the base `status` field — an approved or rejected contradiction note stayed `status: draft` forever, alongside its now-settled `review_state`. Fixed in the same commit that fixed the regex bug above (`review-queue.ts` now writes `status: active`/`status: rejected` alongside `review_state`).
- **The base `status` field generally:** every writer in the codebase set it once, at note-creation time, and nothing ever transitioned it afterward — no promotion path, no demotion path, no archival path, for any note type. Sub-project C gave `source_summary` notes a real `draft → active` promotion (at the exact point the pipeline already stamps `ingest_status: 'linked'`) and a real `draft → archived` terminal state for notes that never get processed.

## 4. Cost and the safety/tier system now in place

- **`BudgetTracker`** (`src/shared/budget.ts`) issues per-tier daily LLM-call reservations (defaults: `fast: 200, medium: 50, heavy: 10`), persisted to `.karpathy/state/budget.json`, rolling over at local midnight. Every new LLM-calling feature added by these sub-projects (significance gate, review analysis, glossary synthesis, topic/decision/project refresh, research execution) reserves a slot before calling out; on refusal, the job returns without doing partial or corrupting work and is safely retried on the next cycle.
- **Tier-aware model selection:** `config.llm.models.{fast,medium,heavy}` existed in config with sensible defaults but **nothing read it** before B2a — every call used the single `config.llm.model` regardless of intent. `createLLMFromConfig(config, stateDir, tier)` now selects the right model per call site; research execution went from always using the same model regardless of depth (`light`/`medium`/`heavy` differed only in round count, never model) to `light→fast, medium→medium, heavy→heavy`.
- **Cheap-first-with-escalation:** the pattern established by B2a's `generateReviewAnalysis` (try `fast`, escalate to `medium` only if confidence is below `config.review.confidenceEscalationThreshold`, default 0.7) is now the standard shape reused by research execution and effectively established as this codebase's house style for balancing quality against cost.
- **Connectivity-probe cache:** avoids wasting real HTTP attempts against a LiteLLM proxy that's down because of VPN disconnection — one job's real failed attempt protects other pending jobs from also burning a call during the same outage window (2-minute trust window, per-provider so a LiteLLM outage doesn't also block Bedrock-backed jobs).
- **Indefinite-but-bounded retry:** transient failures (network errors, HTTP 401/403/429/5xx — auth rejections during a VPN outage are explicitly always classified transient) retry with exponential backoff capped at 30 minutes, rather than being discarded after ~7 seconds; one Slack alert fires per unbroken failure streak past 1 hour so a genuinely dead credential doesn't retry forever silently.
- **Net effect on real spend:** before this work, actual LLM cost was near-zero largely because the mechanisms that would spend money weren't running (gate never called, research-execute never scheduled, `intel tick` never actually reaching LiteLLM). The real cost exposure going forward is now bounded by the daily tier caps above, not by whatever an unthrottled ingest pipeline would have generated once these mechanisms started working.

## 5. What was broken and got fixed, by sub-project

### Sub-project A — Quality Layer Activation
Three fully-built, fully-inert mechanisms wired into place: scheduled contradiction/duplicate/entity-dedup detection behind a now-meaningful `reviewEnabled` flag; entity-dedup auto-merge routing (≥85% confidence auto-merges, below routes to human review); the significance gate wired into the actual production ingest choke-point (`compiler.ts`), with a new confidence-gated "uncertain drop → create page but flag for review" path instead of guessing. Root-caused: Claude Code's own `Glob`/`Read` tool invocations and system state/config files had been becoming permanent wiki pages because the gate never ran on the real ingest path.

### Sub-project B1 — Taxonomy & Extraction Redesign
Found and fixed three previously-unknown defects: `action_items` was extracted by the LLM every time but silently stripped by a schema that had no field for it (Zod non-strict parsing discards unknown keys) — decisions and to-dos had been conflated partly *because* the pipeline was already discarding the signal that would separate them. Decision-note synthesis was structurally broken by a prompt/protected-region label mismatch (detailed above). `project_slug` was computed and persisted but dropped from every downstream job payload, so self-referential (karpathy-developing-itself) content couldn't be filtered from curation even though the tag existed end-to-end. Also consolidated 37 thin concept pages into one glossary and broadened tool/organization noise filtering (2 known-bad organization entries — Workfront, "Claude Max Enterprise" — corrected; both are products/tiers, not organizations).

### VPN-aware LLM retry (infrastructure prerequisite)
Found that `karpathy intel tick` — the actual cron-wired job-runner entrypoint — would never have made a real LiteLLM call at all, because its client factory only branched on `bedrock` and silently fell back to a no-op client for any other provider, including the newly-chosen `litellm` default. Consolidated four divergent, partially-broken LLM-client factories into one correct shared one. Added `TransientLLMError` classification and an indefinite-but-capped retry lane so a job that fails during a VPN outage resumes instead of being discarded.

### Sub-project B2a — Review-Note Explanatory Content
Found that only 2 of the 4 review-note-writing code paths shared a common write function (contrary to the initial assumption when this sub-project was scoped) — contradiction and duplicate detectors each duplicated their own inline frontmatter-writing logic. All four now write real LLM-generated analysis via one shared `generateReviewAnalysis` orchestrator, with the fast→medium escalation pattern described above. Also found and fixed a latent bug: `llmGate()`'s empty-candidates short-circuit meant the LLM would never actually be invoked once wired in — every call would have silently fallen back to the heuristic result.

### Sub-project B2b — Wiki Content Richness
Found and fixed the two layout-hardcoding bugs described in §2 above (project hubs) and a third, latent one: `topic-refresh.ts` hardcoded a single region name (`current-understanding`) that doesn't exist on `decision`/`project`/`project_spec` notes — the first time refresh actually fired on one of those types (it hadn't yet, in this vault), it would have bolted a disconnected new section onto the end of the note instead of fixing the actually-thin region. Generalized the refresh mechanism into a `REFRESH_TARGETS` registry so decision/project notes get their own region-correct synthesis. Added a deterministic thin-content detector (no LLM) so the ~24 already-placeholder notes get force-enqueued for refresh immediately rather than waiting months for natural staleness decay.

### Sub-project B2c — Person Name Resolution
Found the proven Bryan/Pino duplicate-detection blind spot described in §3. Added Slack-handle external-ID capture (deterministic, no LLM) as the highest-confidence resolution tier; honorific stripping, a curated nickname-equivalence table, and initials matching for person-kind fuzzy matching; and a person-scoped, no-shared-source-required name-variant detector feeding the existing human-reviewed reconciliation queue. Also fixed a wikilink-hygiene defect found on `Matt Newman.md` (a full vault-path wikilink instead of bare-slug form, which the merge-rewrite mechanism can't match on).

### Sub-project C — Draft/Archival Lifecycle
Found that the base `status` field is write-once everywhere in the codebase (§3 above), that 96.8% of all source files are permanently `status: draft`, and that decay-scan's `archive_candidate` write was dead code with a latent bug (never cleared once set, zero read sites, zero test coverage). Gave `source_summary` notes a real draft→active promotion and a real draft→archived terminal state; built an archive queue (mirroring Sub-project A's reconciliation-queue pattern) that finally gives rot-scan's already-computed, already-displayed candidate list — proven live by a real example (the concept glossary itself was rot-scan's one flagged candidate at design time) — an actual action path via a new `karpathy archivist` CLI and `resolve_archive_candidate` MCP tool. Closed the loop in both directions: archival is reversible automatically the moment a note is genuinely re-engaged with.

### Sub-project D — Research Queue Redesign
Found that two of the three documented research-approval surfaces were silently broken against any non-default (`Curated/`-style) layout — every real call returned "queue is empty" or "slug not in queue" against a real, populated 30-candidate queue, for the entire 2.5-month history. `research-execute` had never once been scheduled or run against the real vault. ~19 of 30 real candidates were orphaned by B1's own concept-glossary migration. `research-execute` made unbudgeted, non-tier-aware LLM calls (heavy-depth research used the same model as light-depth). A gap-score formula bug scored an unset confidence field (0.7) as *more* urgent than an explicitly medium-confidence one (0.5) — backwards. All four are fixed; auto-drain (decided candidates automatically executing) was built and tested but shipped off by default, since `research-execute` — and the external websearch subprocess it depends on — has never once been exercised against real traffic.

## 6. Recurring bug patterns (cross-cutting, not sub-project-specific)

These three patterns each showed up independently across multiple, unrelated sub-projects — worth calling out on their own because each is individually significant, not just a symptom of one feature.

### Pattern 1 — Layout hardcoding (`wiki/` instead of the configured `layout.wiki`)

At least **12 separate commits**, across nearly every sub-project, fixed a hardcoded default-layout path (`wiki/`, `wiki/_system/`) instead of reading the vault's real configured layout (`Curated/wiki`, `Curated/_system` in Tom's production vault):

```

ba91c7e fix(bin): thread layout through intel queue/approve/status research-queue calls
643a8ad fix(mcp): thread layout through approve_research's research-queue read/write
2a8d208 fix(mcp,bin): thread layout through mergeEntities/rebuildAllIndexes call sites
919bf53 fix(compilation): add person name-variant tier to detectMergeCandidates; pass configured layout into detect-entity-dupes
b17bb41 fix(jobs): use configured layout.wiki instead of hardcoded 'wiki/' in check-confidence-decay and agent-synthesize-project
258aa9d fix(cross-linker): thread real vault layout into crossLinkPages' entity index
5e28853 fix(lint): thread real vault layout into buildGraph + lintWiki's entity index
49606fa fix(karpathy-cli): thread real vault layout into mergeCommand's resolveEntity calls
838cdea fix(agent-tools): thread real vault layout into resolve_entity + create_entity
5718117 fix(link-concepts): thread real vault layout into entity index + resolution
e7d82e3 fix(topic-refresh): thread real vault layout into neighbor-cascade entity index
9556bc5 fix(entity-merger): thread real vault layout through merge + wikilink rewrite, not DEFAULT_LAYOUT
```

The pattern is always the same shape: a function takes an optional `layout` parameter defaulting to `DEFAULT_LAYOUT` (the legacy `wiki/` structure), a real call site omits the argument, and the function silently operates on a path that has never existed in the real, `Curated/`-layout production vault — returning empty results, "not found," or writing to a second, divergent file, with no error. Sub-project B2b's own text names the specific reason this keeps recurring: `2nd-brain/product.md`'s frontmatter documents an earlier, dedicated layout-migration pass ("4 bugs fixed in `compiler.ts`, `backlinks.ts`, `update-backlinks.ts`, `rebuild-index.ts`, and `indexes.ts`") that evidently didn't catch every call site, and Sub-project D's own root-cause analysis is explicit: **every test fixture in the affected module used the default layout by construction**, which is exactly why a bug that only manifests under a non-default layout ships invisibly, repeatedly. This is also the exact lesson already captured in the user's own persistent memory (`feedback_layout_aware_paths.md`: *"Always use `layoutFromConfig(config)`/`kindToFolder()`; hardcoded `'wiki/'` breaks Curated/wiki/ production layout"*) — a pattern known and named before this audit, and still found 12 more times over the course of it. Several sub-projects (B2c, D) responded by adding non-default-layout test fixtures specifically to close this blind spot going forward, not just fixing the immediate instance.

### Pattern 2 — `TransientLLMError` swallowing

At least **6 separate commits** found and fixed pre-existing `try/catch` blocks that silently absorbed a transient network failure (VPN outage, rate limit, 5xx) as if it were a permanent one — converting what should have been "retry this job later" into "log an error and quietly proceed as if nothing happened," typically producing a placeholder or degraded result instead of the real content, with no visible failure:

```
25f1c10 fix(jobs): let TransientLLMError propagate through link-concepts ambiguous-entity resolution
7474601 feat(review): generate real analysis for uncertain-drop review notes; let TransientLLMError propagate through the write
1832d05 fix(digest): propagate TransientLLMError through labelCluster instead of swallowing it
393c230 fix(enrichment): propagate TransientLLMError through significance gate and web enrichment
754af4d fix(jobs): propagate TransientLLMError through re-enrich-note.ts (missed in Task 8)
982ecd8 fix(jobs): abort instead of swallowing TransientLLMError in three LLM-calling paths
```

Each was a pre-existing `try { ... } catch (err) { log.error(...) }` block, originally written so one entity's or one page's failure wouldn't abort an otherwise-successful batch — a reasonable intent, but one that had never been updated to distinguish "this specific thing failed" from "the network is down right now." Once the VPN-retry work introduced `TransientLLMError` as a distinguishable type, every one of these call sites needed the same one-line fix (`if (err instanceof TransientLLMError) throw err;`) to let the error propagate and let the job queue's new indefinite-retry lane do its job — several of these were caught specifically during B2a's and Sub-project D's own review passes, after the initial VPN-retry work had already fixed the four call sites it knew about at design time.

### Pattern 3 — The review approve/reject regex bug

A single, independent, and more serious defect, found during Sub-project C's implementation: `karpathy review approve` and `karpathy review reject` had been **silently no-op'ing on every real review item since the review workflow first shipped** (commit `b33675b`). `createReviewItem` — the sole real producer of `review/*.md` notes — serializes frontmatter as `key: JSON.stringify(value)`, quoting every scalar (e.g. `status: "draft"`). `approveReviewItem`/`rejectReviewItem` mutated fields via raw string regex like `/status: \w+/`, which requires an unquoted word character immediately after the colon — a pattern that **can never match a quoted value**. The regex simply failed to match, `.replace()` returned the original string unchanged, and the file was written back byte-for-byte identical. Confirmed with a direct repro against real `createReviewItem` output, not inferred. This bug pre-dated Sub-project C entirely — it was already broken in production before this audit — and was only caught because Sub-project C's own G5 task added a *third* instance of the identical mistake (`status: \w+`) while wiring in a new field, at which point a whole-branch review caught all three at once. The fix replaces every regex-replace with a `parseNote`/`serializeNote` round-trip (this project's standard, quoting-safe frontmatter mutation pattern), and the test fixtures were rebuilt to be produced by the real `createReviewItem()` entry point rather than hand-typed unquoted YAML — specifically so a fixture that no longer matches real on-disk shape can't hide this bug class again.

### Safety defaults deliberately left off (operator action required)

Three flags exist, are fully built and tested, and were deliberately shipped **off** because flipping them changes real production state or spends real money the moment they're enabled — each sub-project's design doc explicitly frames this as Tom's call, not something to default on unilaterally.

| Flag | Default | What turning it on does | Why it's off |
|---|---|---|---|
| `maintenance.reviewEnabled` | `false` (confirmed still `false` in the real live config as of every design doc through 2026-07-31) | Schedules `detect-contradictions`/`detect-duplicates`/`detect-entity-dupes` daily instead of manual-CLI-only | Pre-dates this audit as a deliberate off-by-default setting; every sub-project that touched adjacent code (B2c, C) flagged it as still off and recommended flipping it, without doing so themselves |

No code path anywhere in the repository sets any of these three flags to `true` or bypasses reading them from config — confirmed by inspection in each relevant design doc. Flipping them is a one-line edit to `~/.karpathy/config.json`, entirely outside this git repository.

## 8. Bottom line

The audit found a system that captures continuously and well (11,876 raw sources over 2.5 months, no evidence of ingestion itself failing) but whose curation layer was, for most content types, either never running, running against the wrong path, or producing placeholder output — not because the underlying mechanisms were poorly designed, but because a small number of specific, findable defects (a dead config flag, four unscheduled jobs, a handful of hardcoded paths, one quoting-format mismatch in a regex) sat quietly in the gap between "the code exists" and "the code runs against real production data." Eight sub-projects closed essentially every gap that could be closed without either redesigning the extraction pipeline or Tom personally deciding to switch on a mechanism that spends money or mutates thousands of real files at once. What's left is one clearly-named, high-priority follow-up (why 93.7% of ingested content never gets processed) and three flags sitting one config edit away from Tom's own go-ahead.
